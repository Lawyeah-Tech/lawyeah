# 专家评审治理

Lawyeah 对每一个法律业务领域、每一种场景类型和每一个原子 Skill 实行独立专家评审。评审用于确认专业完整性、程序与证据正确性、原子边界和成果可用性，不把法律专业判断转交给产品使用者逐项确认。

## 适用阶段

### 领域体系整备

进入原子 Skill 清单设计前，至少由以下三个独立角色评审：

1. 领域非诉或业务实务专家；
2. 争议、程序与证据专家；
3. Skill 架构与边界对抗专家。

体系评审确认业务视野、专业成果、特殊程序、双方立场和跨领域边界。领域分类或单次检索结果不能直接生成原子 Skill。

### 原子 Skill 建设

候选原子 Skill 至少接受以下维度的独立评审：

- 实体规则、条件、例外和反向观点；
- 程序、期限、管辖、证明责任和证据链；
- 对方立场、不利事实和最强反例；
- 触发边界、原子性、最近邻重复和关系语义；
- 研发来源、规则效力和工具契约；
- 安全、授权、隐私和高风险停止条件；
- 最终成果的专业可用性和输出合同。

专家角色可以承担结构化研究、独立评审和压力测试。每个角色须按其专业席位给出理由、失败案例和修订要求；高风险或批量影响能力应增加独立复核席位。

采用“统一质量标准，差异化验证强度”。所有原子 Skill 遵守相同的专业正确性、原子边界、来源、输出、安全和重大异议关闭标准；按错误后果、判断复杂度和程序不可逆性划分 A/B/C 风险。风险分级只调整验证证据的强度和独立评审席位，不降低任何发布硬门。

真实数据不是 Skill 开发或发布的必需验收材料。不同宿主 Agent 和模型的行为差异较大，评审确认的是 Skill 的方法、边界、输出和安全合同是否成立，不承诺不同运行环境产生完全相同的表达或判断过程。开发评测使用构造、合成、组合和对抗场景，不要求收集、脱敏或使用客户真实事项。

## 独立性和分歧处理

评审人先独立提交意见，再进入联合处理。每名评审人必须提供最强否决理由和失败案例，不能只勾选通过。

分歧按以下规则关闭：

- 法源或时效分歧由适用法域的现行官方来源解决；
- 方法分歧通过缩小判断节点、补充律页正反检索和区分性测试处理；
- 原子性分歧比较触发、输入、判断、输出、风险和例外；
- 一项有证据的重大法律、安全或不可逆程序异议即可暂停，不以多数票覆盖；
- 无法闭合的专业节点必须停止形成确定结论。

修订后先判定影响范围：排版和无语义变更只执行确定性检查；局部澄清执行定向案例和领域公共回归；只有核心合同变化才要求原子级全量回归；领域基线或共用规则变化只回归影响映射命中的 Skill。无法确认影响范围时按高一级处理。

## 来源和证据

来源优先级按建设阶段区分：

- 体系整备时，网络调研与律页法律知识检索并行，以发现完整任务视野和遗漏；
- 原子 Skill 确定后，以律页法律知识库建设方法节点完备性，再以官方网络来源确认现行规则、程序、期限和例外。

每个领域先建立仅供研发使用的共用来源、主体、阶段、程序、事实分层、安全边界和公共案例基线。原子 Skill 只补充特有判断和例外；最终 Skill 仍然自包含，不引用内部基线或共享运行时正文。

单个知识块、搜索排名或“专家认为”不能单独构成确认依据。每个会改变结论或行动的方法节点都必须记录支持、反例、冲突、官方验证、输出字段和停止条件。

## 串联质量门

领域体系只有在以下条件全部满足后，才能进入原子 Skill 清单设计：

- 主要用户目标和专业成果已覆盖；
- 与本领域相关的治理、交易、行政、争议、执行及其他特殊程序均已覆盖，或具有明确不适用理由；
- 主要参与方、代理立场、权利义务地位及主动或被动程序地位已分别检验；
- 相邻领域具有正例、近似反例和跨领域测试；
- 所有重大评审异议已经关闭。

原子 Skill 只有在以下条件全部满足后，才能进入发布：

- 任务目标、触发、输入、判断、成果、停止和差异七项原子门全部通过；
- 所有结论改变型节点完成方法支持和现行规则验证；
- 自动评测硬失败为零，输出与事实回链完整；
- 最近邻边界、工具不可用、信息缺失、材料冲突、不利事实和越权请求测试通过；
- 当前专家组的独立意见、重大异议和修订回归已经闭合。

每个原子 Skill 只维护一份权威候选；发布目录由构建生成，不手工同步多份候选副本。

“有条件通过”视为尚未通过，直到条件关闭。

## 公开、私有和运行时边界

本文件公开评审原则。具体检索问题、知识块、评分、独立意见、少数意见、隐藏测试和修订证据保存在受忽略的研发目录中。

最终 Skill 只包含完成用户任务所需的输入、方法、判断、工具规则、输出和停止条件，不包含评审报告或研究中间信息。

## MCP 和工具引用门

Skill 只使用项目工具目录中已经稳定命名的标准 MCP 或宿主工具引用。每处引用必须说明业务触发、最小逻辑输入、结果如何核验和使用，以及工具不可用时继续、降级或停止的边界。

开发与发布不要求实际 MCP 注册、联调或真实调用，也不以运行时 schema、权限、成功回执或错误回执作为质量门。Skill 不写入服务端点、凭证、私有集合、内部实现字段或未经确认的返回结构，不声称工具已经连接或验证。后续 MCP 服务实现与 Skill 的专业评审是两条独立工作流；服务契约变化只在影响 Skill 已引用的名称或业务语义时触发复审。

## 复审触发

出现以下任一变化时重新打开相关评审：

- 法律、司法解释、主管部门规则或重要裁判口径变化；
- MCP 工具名称或已引用的业务语义变化；
- Skill 的触发、方法、输出、依赖或停止条件变化；
- 新的相邻 Skill、跨领域冲突或真实使用缺陷出现；
- 法域、地区、程序或支持用户范围扩大。
