# 最小必要方法

本文件是可执行判断节点，不是栏目说明书。每个会改变合法性、路径、时限或对外含义的节点，必须回链来源编号、规则核验状态、最强反方和停止条件。

判断只用 `现有依据支持`、`现有依据不支持`、`依据不足，无法形成结论`。不得输出胜诉率、必然免罚、必然合法或唯一处罚金额。未知人数或金额不写零。

`search_law` 返回已失效《合同法》及其解释时记为噪声，不得写入 `L#`。MCP 效力字段与有权机关公布的施行日冲突时，以施行日为准并记录冲突；无法独立核验施行日则该规则字段停止。

## Q# 矩阵

固定列：`编号｜目的｜种类／权限｜是否基本功能必需｜拒绝后果｜超收红旗｜判断｜待核`。

---

## 节点 0　专项分流

先于实体判断。命中任一项则整案转出，本任务只交付分流理由和最小交接，不填本任务实体结论。

| 信号 | 转出 |
| --- | --- |
| 商业秘密、专利商标著作权权利本身 | 知识产权领域 |
| 企业级合规体系、反商业贿赂、舞弊内部调查 | 企业合规领域 |
| 诊疗过错、病历鉴定、药品器械或医疗机构监管本身 | 医疗医药领域 |
| 解除、处分、民主程序等劳动法后果为主 | 劳动领域 |
| 侵犯公民个人信息罪控告或辩护 | 刑事领域 |
| 一般交易合同签前审查起草 | 审查起草领域（本窗搁置，只说明不实施） |

混合信号：本任务主轴可留；专项只作为背景时在缺口标明，不把专项规则硬套进本任务结论。

## 节点 1　分流

- 若 主问题是同意效力或单独同意：则 转同意原子
- 若 主问题是不授权就关基本功能的交互设计：则 转捆绑同意原子
- 若 主问题是第 13 条哪一项成立：则 转合法性原子
- 若 用户只要 C 端 App 审查清单：则 只分流，不回改该商品

## 节点 2　目的

- 若 目的写成“运营需要”或“数据驱动”：则 目的不特定，必要性依据不足
- 若 实际使用与告知目的不一致：则 目的外使用红旗，相关种类必要性不支持

## 节点 3　对照

- 若 通讯录、短信、相册与核心功能无直接关系：则 现有依据不支持必要
- 若 一次性功能却要求持续权限：则 持续收集不支持
- 若 行业必要范围已核验且种类在列：则 必要可支持，仍不得超用途使用
- 若 行业清单未核验：则 必要字段停止，不编造唯一清单

## 节点 4　基本与附加

- 若 定位仅用于附近推荐：则 附加功能，可拒
- 若 支付风控所需的有限设备信息：则 可列为该功能必要，但不得顺带画像
- 若 拒绝附加功能后基本功能不可用：则 打开捆绑原子

## 节点 5　输出切割

- 若 部分种类超收：则 只否定超收种类，不把整案写成全部违法
- 若 用户要下架整改报告：则 转下架原子

## 金额与规模

已知处理人数、事件波及人数、上一年度营业额只作区间参数。未知不写零。个保法第 66 条处罚上限只标接口，不输出唯一罚款预测。
