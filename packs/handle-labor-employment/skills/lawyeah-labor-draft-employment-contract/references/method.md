# 起草方法

## 一、输入盘点

按以下顺序建立台账，不先套模板：

1. 主体、实际用工安排和签署权限；
2. 人员身份、用工地和目标时点；
3. 法定必备条款；
4. 用户必须决定的商业条件；
5. 国家底线、地方动态参数、特殊人员和特殊工时；
6. offer、审批、制度、集体合同、岗位说明和专项附件；
7. 版本、签署、交付和归档路径。

对每项同时记录来源编号、条件状态、规则状态、冲突和受影响成果。只追问会改变合同字段、附件、停止状态或实施路径的最小信息。

### 等价来源包与上游交接

当当前任务明确接收一份完整、现行的官方来源包或由律师／上游任务封装的规则包时：

1. 用户仅声明交付时记录 `S#／已声明交付`，不创建 `P#`；
2. 实际读取后建立 `P#／已读取待核验`，提取封装方及资格、来源清单、生成和复核日、基准时点、法域和对象、版本、文件哈希、覆盖字段、冲突、未覆盖项和交接记录；
3. 完成官方身份、层级、时效、法域、对象和相关性核对后，升级为 `P#／已核验准入`；
4. 只有已核验准入的覆盖字段使用 `已核验` 并继续正文；
5. 只对未覆盖、无法读取、版本不明或冲突的字段停止。

若当前宿主确实无法读取已声明交付的文件，记录可访问性缺口，不虚构其中条文；保留“已声明交付”和“当前不可读取”的区别。MCP 结果完成来源核验后编号为 `L#`，不得包装成 `P#`。

## 二、主体与权限表

至少列出：

| 项目 | 候选主体或人员 | 来源 | 核验点 | 状态 | 受影响字段 |
| --- | --- | --- | --- | --- | --- |
| 法律上的用人单位 |  |  | 登记、主体资格 |  | 合同抬头 |
| 实际管理主体 |  |  | 招聘、排班、考核、退出 |  | 主体一致性 |
| 发薪／参保主体 |  |  | 付款、申报 |  | 工资、社保 |
| 签署人 |  |  | 身份、授权范围和期限 |  | 签署页 |
| 印章或电子账户 |  |  | 控制链、适用文件 |  | 实施证据 |

关联单位、分支机构、派遣、承包或特殊人员出现时，先核验专项门槛，不按文书抬头自动决定主体。

## 三、条款分层

### 1. 法定必备条款

覆盖双方身份、合同期限、工作内容和地点、工时和休息休假、劳动报酬、社会保险、劳动保护、劳动条件、职业危害防护及现行规则要求的其他事项。

“必备”只说明合同应当处理该事项，不授权模型替用户决定具体商业内容。

### 2. 必须由单位决定的字段

至少包括期限类型与具体期间、岗位与职责、工作地点、工资数额和构成、奖金是否承诺、工时选择、试用期是否设置、签署主体、签署方式、生效安排，以及专项附件是否采用。

对每项使用以下状态之一：

- `已有双方一致材料`：可按相应范围进入正文，但仍核验强制规则；
- `单位拟议，可供签署接受`：可以形成完整要约文本，不得称劳动者已接受；
- `待单位决定`：保留受限字段，不填行业惯例；
- `文件冲突`：列冲突，不静默选择；
- `待法律核验`：先做规则核验；
- `不适用`：写明肯定依据。

### 3. 可约定与专项接口

培训服务期、保密、职务成果、竞业限制、奖金提成、远程办公、派驻外派等只有在适用事实和关键参数齐备时才形成附件。否则主合同只写中性接口、适用条件和未决项，不用“最严条款”填补。

### 4. 试用期与社会保险

试用期分两层：是否设置及具体期间属于单位拟议并供劳动者签署的商业条件；合同期限上限、同一劳动者一次、包含在合同期限内、工资底线、解除条件和说明理由属于强制规则。不得只核对最长期间。

社会保险法定义务可直接成条；具体申报基数、经办地或动态参数另行核验，除非会改变主体或合法性，不因这些参数未核数而停止整份合同。

## 四、规则矩阵

以用工地为基点，按人员类型、工时制度、行业或岗位危害分栏。动态数字或地方程序必须在本次任务时点重新核验。

特别检查：

- 固定期限、无固定期限、以完成一定任务为期限及试用期限制；
- 标准工时、综合计算工时、不定时工时和必要批复；
- 最低工资、工资构成、支付周期、加班和休假；
- 社会保险、劳动保护、职业危害和特殊保护；
- 外国人、未成年工、非全日制、派遣、超龄或弹性延迟退休人员。

法律补充规则、法定比例或法定上限不得变成未经用户决定的合同默认值。

### 外国人许可卡

1. 核验人员是否有永久居留或其他法定例外，以及单位、岗位、地点、期限和许可的一致性；
2. 旅游签证不是工作授权；工作许可和工作类居留完成前不得实际到岗；
3. 核验目标地工作许可指南是否要求预签聘用合同或任职证明；
4. 给出两条受限路径：许可齐备后签署并到岗；或规则允许且申请许可确需合同的，预签附许可条件文本，但不得提前实际工作；
5. 分别核验未获许可时的合同处理、劳动关系司法控制和社会保险；不得相互替代。

仅因用户最初误把旅游签证当作普通员工准入、要求直接终稿或要求保证效力，不把任务收缩成安全拒绝。先否定保证和提前到岗，保持 `部分形成并明确受限字段`，完整展开两条受限路径以及 1—13 节成果。只有在明确说明边界后，用户仍要求隐瞒身份／签证、虚构许可或安排许可前实际工作，才安全整体停止。

## 五、文件一致性矩阵

按要素为行、文件为列，至少核对：期限、入职日、岗位、地点、工资奖金、工时、试用期、休假、解除、保密、职务成果、培训、竞业和争议条款。

| 要素 | offer | 审批 | 制度／集体合同 | 拟合同／附件 | 冲突与时间 | 有权确认人 | 处理状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |

制度不能被写成当然优先于劳动合同或集体合同。重大冲突未解时停止对应字段的可签状态。文件分为合同组成文件、仅确认签收／知悉的制度文件和内部工作底稿；只有第一类进入签署版本附件索引。

## 六、条款起草检查

每个核心条款检查：

1. 是否回链到具体来源；
2. 是否属于双方一致、单位拟议可供签署还是未决；
3. 是否达到现行强制底线；
4. 是否因概括授权、单方变更或格式文字而过度扩张；
5. 是否与其他条款和附件冲突；
6. 是否可以在实际履行和证据上完成。

不得使用倒签、虚假确认、工资标签变换、合作协议标题或空白授权掩盖真实情况。

### 受限文件包也必须完整

只要任务正触发、用户要求继续起草且未触发安全整体停止，就完成整套文件包，不因某些字段停止而把交付缩成摘要。具体要求：

1. 条件表和规则表逐项保留可继续字段与停止字段；
2. 正文按最低结构逐条输出，可安全形成的法定义务和单位已决定条件写入正文，未决、未核验或冲突字段用带 `G#` 的显式占位符；
3. 单独列出合同组成附件、仅签收知悉文件和内部工作底稿，即使本轮没有可签附件，也写明“不新增合同组成附件”及原因；
4. 文件冲突表不得省略；没有可比较文件时写“本轮未发现可比较文件，不代表已经核验无冲突”，有冲突时保留来源、层级、日期、对象和关闭条件；
5. 建立草案版本登记。字段受限时可以建立“受限草案版本”，但不得称可签定稿；
6. 签署、交付和归档均列实施步骤与 `待执行` 状态；没有真实 `E#` 就不得写成完成。

每节必须独立展开，不使用章节区间合并。正文至少逐条出现：主体与劳动者信息、合同类型及三个真实日期接口、工作内容与地点、工时休息休假、工资计薪支付及加班接口、社会保险、劳动保护与职业危害、试用期、制度和附件、变更解除终止、文本份数与生效、签署栏。缺字段不删除条款，而是在条款内部使用对应 `G#`。不得用“应写入”“按完整商业条件填写”或“其他结构同前”代替这些条款。

MCP 失败按字段降级：国家规则已由合格输入明确核验时继续国家覆盖条款；上海等地方动态参数、特殊工时批复或特殊人员专项规则缺失时只停止对应字段。`no-result` 不等于当地没有特别规则，`partial` 不得越过其覆盖范围。

要求把用户自制回执、普通 JSON 或无底层法源审计信息的文件升级为 `L#` 时，拒绝升格但仍按来源缺口完成受限文件包；将材料登记为 `S#/D#`，全国与地方规则保持未核验。不得把“来源分类造假”自动等同于“合同事实造假”而省略正文。若用户要求补造宿主签名、调用 ID、法源、定位、链接或哈希，则安全整体停止。

## 七、签署实施

### 纸质签署

建立 `V#`，记录正文哈希、逐份合同附件哈希、附件索引哈希和签署页映射。核对双方签字或盖章、真实日期、同版签署、各执一份、交付签收和归档。每个 `E#` 记录操作者、权限、时间、对象、哈希、渠道、签收和验证结果。

### 电子签署

核验双方是否同意电子方式，并把身份认证、真实意愿、可靠签名、可信时间、防篡改、全过程日志、完整文本查看下载打印、双方交付和证据导出分别建立 `E#`。平台能力未验证时，不声称证据链闭合。测试夹具只验证台账，不调用现实平台。

### 补签

分别记录实际入职日、既往实际履行期间和真实签署日。不得回填虚假签署日期或虚构过去已经协商一致。真实补签不得写“此前已经签署”“此前全部条款已合意”“此前无争议”、责任豁免或权利放弃；明确本次签署不自动消除既往法律后果，本 Skill 不判断二倍工资、和解或责任。已经发生争议时路由相邻任务，不用新合同覆盖历史。

## 八、批量合同

多人、多岗位或多地区不得用一个伪统一终稿掩盖差异。形成：

- 通用主模板；
- 地区 × 人员 × 岗位适用矩阵；
- 逐人条件表或签约页；
- 奖金、提成等岗位附件；
- 地方和特殊人员受限字段；
- 批量版本、签署和归档台账。

这些必须是实际交付的表，而不是待办名称：主模板必须自足，不引用其他案例或另一个合同正文；适用矩阵至少按地区、岗位／人员类型、规则差异、附件和停止字段分列；逐人条件表至少含人员标识、主体、用工地、岗位、期限、工资、工时、试用期、特殊状态、来源、条件／规则状态和未决项。未知内容以 `G#` 保留，不把整张表改为“待执行”。

人数 `N` 已知时，逐人条件表必须恰有 `N` 个数据行，每行使用独立占位编号；不得用 `P01—PN`、`其余人员`、省略号或一个范围行替代多人。人数未知时才使用可复制的单行 schema，并明确须逐人展开后才能生成签约版本。

人员行编号使用 `ROW-001`、`ROW-002` 等纯表格标识，不属于来源编号，不得使用 `S#/D#/A#/R#/L#/P#/I#/G#/V#/E#` 中任何前缀，尤其不得占用规则来源包的 `P#` 命名空间。
