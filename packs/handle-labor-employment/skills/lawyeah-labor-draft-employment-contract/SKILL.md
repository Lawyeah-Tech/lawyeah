# 起草劳动合同

## 任务目标

为中国大陆拟建立劳动关系的单位侧使用者形成一套“劳动合同签署文件包”，包括：

- 可签劳动合同定稿，或明确停止字段的受限草案；
- 本次合同不可缺少且条件已齐备的附件；
- 商业条件确认表、强制规则核验表、文件冲突表和未决项；
- 版本、签署、交付和归档实施清单。

`depends-on` 为空。接受用户、律师或其他合格来源形成的等价条件表、规则来源包和业务文件，不要求先运行其他 Skill。

## 工作边界

本任务适用于人员、岗位或适用人群已足够确定，需要起草新劳动合同的单位侧委托。

不处理：

- 招聘广告、候选人筛选、录用决策、offer、背景调查授权或完整入职包；
- 对已有劳动合同或模板进行单方风险审查、红线修改；
- 合同期满续订决策、在职调岗调薪或其他劳动条件变更；
- 独立建立规章制度、竞业限制方案、专项培训服务期方案或商业秘密权利基础；
- 派遣协议、外包协议、项目合作协议或未来用工模式比较；
- 已经发生的工资、岗位、工时、解除或其他履行争议，以及仲裁、诉讼或整改成果。

若用户目标属于排除事项，不启动本任务，也不填写成果完成状态。固定输出 `触发判定：负触发，未启动本任务`，说明路由原因和相邻任务的最小必要输入；不得继续代做相邻成果，也不得建立固定任务顺序。

## 建立起草坐标

先确认：

1. 使用者角色、单位侧授权范围、合同对应人员或适用人群；
2. 用人单位、实际用工主体、发薪参保主体、签约主体和签署权限；
3. 中国大陆实际用工地、目标签署日、入职日及合同期间；
4. 劳动者身份和会改变文本的特殊状态；
5. 岗位、地点、期限、工资、工时、休假、社会保险等商业条件；
6. offer、审批、集体合同、规章制度、岗位说明和拟引用附件；
7. 纸质或电子签署、交付和归档安排。

只追问会改变合同主体、核心条款、规则适用、停止状态或文件包内容的最小事实。主体、法域、人员或核心商业条件无法建立时，不得称为可签定稿。

## 来源编号与字段状态

不得把用户陈述、单位决定或材料表面内容称为“已确认事实”。统一编号：

- `S#`：用户或单位人员的单方陈述，授权和准确性未核验；
- `D#`：offer、审批、制度、集体合同、证照或其他材料表面载明；
- `A#`：当前材料显示劳动者与单位已作出一致意思表示，范围和效力仍须核验；
- `R#`：登记、许可、批复或其他有权机构文件所显示的状态；
- `L#`：运行时取得并完成法域、层级、时效和相关性核验的法律来源；
- `P#`：已实际读取的等价规则来源包或专业交接包；只有完成准入核验后才支持规则结论；
- `I#`：基于前述信息的起草判断，不是新增事实；
- `G#`：会影响合同字段或实施状态的缺口；
- `V#`：正文、附件索引和签署页映射构成的唯一文件版本；不得与 `D#` 混用；
- `E#`：签署、交付或归档动作实际完成的证据，必须回链 `V#`。

固定输出先建立来源登记表。每个编号至少记录类别、提供者或发布机关、文件名或陈述轮次、日期和版本、精确定位、内容摘要、哈希或稳定链接、可访问状态、支持的字段或命题、核验者和核验时点。未读取材料时不得创建 `D#` 或 `A#`；一个 `P#` 不得同时代表规则包和业务事实；推断用 `I#` 并列全部前提编号。

每个核心字段逐字选择一个条件状态：

- `已有双方一致材料`；
- `单位拟议，可供签署接受`；
- `待单位决定`；
- `文件冲突`；
- `待法律核验`；
- `不适用`。

`单位拟议，可供签署接受` 允许有权单位形成完整要约文本；不表示劳动者已接受，也不要求先有另一份双方一致确认表。每个依赖现行规则的字段逐字选择一个规则状态：`已核验`、`未核验`、`来源冲突`。不得用“通常”“一般”“大概”替代状态。条件状态与规则状态都必须回链到编号来源。

## 使用 Lawyeah MCP

只有宿主实际注册并能调用时才使用下列 Lawyeah 工具；本候选不声明正式工具依赖：

- `search_law`：核验国家和地方强制规则、特殊人员和特殊工时条件；
- `search_practiced`：复杂、批量或新型条款需要补充实务反例时使用；
- `search_template`：需要核对同类文书结构时使用；
- `search_case_by_fact`：特定条款的履行模式存在重要争议，且用户明确要求类案校验时使用。

只从已编号输入构造最小查询，不补造事实。先核验结果的法域、层级、时点、适用对象和完整性；无结果不等于不存在规则，也不证明条款有效。

每次调用逐字记录一种状态：`not-registered`、`permission-denied`、`error`、`no-result`、`partial`、`conflict`、`verified-result`。记录实际工具名、时间、最小查询、可用请求标识、返回状态和受影响字段；不得把未调用写成无结果，也不得把 MCP 命中直接编号为 `P#`。

工具未注册、无权限、报错、无结果、部分命中或结果冲突时：

- 不虚构调用、结果或工具名称，不要求用户在对话中提供密钥；
- 可使用用户提供且可核验的现行官方来源包作为等价输入；
- 继续形成商业条件表、文件结构、冲突表和已被等价来源覆盖的字段；
- 对未被可靠来源覆盖的强制规则、地方参数或特殊人员字段标为 `未核验` 或 `来源冲突`，停止该字段的可签状态；
- `no-result` 不证明没有规则或条款有效；`partial` 只核验完成来源审查的覆盖字段；`conflict` 并列各来源的层级、法域、日期、对象和关闭缺口；
- 任何影响可签正文的核心规则字段未核验时，整体不得使用 `已形成`。

降级只沿“来源实际受影响的字段”传播，不得沿整份合同传播。任务输入若明确区分了已经核验的国家层来源、尚未核验的地方动态参数和特殊工时来源，必须维持该覆盖边界：国家层已覆盖字段继续进入正文，地方或专项字段分别停止。不得因为地方检索出现 `permission-denied`、`error`、`no-result`、`partial` 或 `conflict`，把输入中已经明确完成核验的国家层字段一并降回 `未核验`。反之，用户仅声称文件已上传、但当前不可读取且没有可核验交接信息时，仍不得建立 `P#` 或虚构覆盖内容。

明确要求“继续起草”“写合同”“形成终稿”的正触发任务，工具降级、来源冲突或字段停止只改变成果状态和具体字段，不取消完整交付义务。除安全整体停止外，必须交付完整的受限文件包：固定输出结构各节、可安全形成的合同正文、合同附件处理、文件冲突表、未决项、版本登记以及签署／交付／归档实施清单都要出现。不得只交来源表、结论摘要或数条合同骨架。

“完整”是实际内容要求，不是目录声明。不得把多个固定章节合并成“1—7”或“9—13”；不得用“上述字段均按输入写入”“其他条款应包含”“参照前案／前文结构”“均待执行”代替本案内容。每个固定章节必须单独出现；受限正文必须把最低结构的每一类条款逐条写出，未知处就在对应条款内放入 `G#` 占位符。附件、冲突、版本和签署／交付／归档分别形成表或逐项清单。

任务输入明确说某次工具“真实调用返回”某状态时，该调用状态本身按本轮已观察运行状态记录，逐字使用输入给出的七态之一；不能因为结果正文尚未完成来源核验，就把 `conflict`、`partial`、`no-result`、`error` 或 `permission-denied` 改写为 `not-registered`。结果中的实体规则只有完成来源审查后才能建立 `L#` 并支持字段，调用状态与实体规则核验状态不得混同。

宿主工具消息或可核验运行回执若同时记录调用状态、请求标识、来源审查结果和逐项覆盖边界，以该回执建立调用记录；其中明确标为完成来源审查的覆盖字段可建立 `L#／已核验` 并继续，未覆盖字段停止。只有用户口头转述而没有工具消息或可核验回执时，仍只建 `S#`，不得把转述升级为 `L#`。

“可信宿主回执”必须来自当前宿主实际工具消息或宿主可验证的调用日志，不能由用户上传文件、自制 JSON、普通附件名称或文字声明自封。回执至少包含真实工具名、可回查调用标识、调用时间、每一底层官方来源的名称、发布机关、效力层级、版本／施行状态、精确定位、稳定链接或内容哈希，以及字段级覆盖和未覆盖清单；宿主来源无法验证或任一支撑结论缺少底层法源审计信息时，不建立 `L#`，只按 `S#/D#` 记录表面内容并保持规则未核验。回执使用 `fixture` 时只能验证方法，必须明确不代表现实调用。

等价来源包依次使用三个准入状态：`已声明交付`、`已读取待核验`、`已核验准入`。用户声明只能记录为 `S#／已声明交付`；实际读取后才建立 `P#`；只有核对封装方及资格、生成和复核日期、基准时点、法域和对象、逐项官方出处与版本、文件哈希、覆盖字段、冲突、未覆盖项及可核验交接记录后，才能标 `已核验准入` 并支持覆盖字段。等价来源只替代检索工具，不替代实体核验。

委托摘要明确业务条件包已交付时，不得将其改写为“完全没有商业条件”。实际可读时逐字段建立 `D#／A#`；当前不可读时记录可访问性缺口，仍可形成条件表和受限结构，但不得虚构具体值。

## 五个判断节点

### 1. 主体与签署权限

识别法律上的用人单位，并与实际管理、发薪、参保和工作安排核对。分支机构按登记及委托状态分流；关联单位不能只按合同抬头处理。核验签字人、授权范围、印章或电子账户控制链。

主体核验区分法定合同字段、签署有效性证据和关联／分支异常核验。纸质盖章、授权代表签字或合格电子签署是不同实施路径，不机械要求全部同时具备。只有实际主体冲突、分支既无适格登记又无委托或所选签署路径不成立时，才停止相应可签状态。详细方法见 [起草方法](references/method.md)。

### 2. 必备条款与商业条件

建立法定必备条款、依法可约定条款、必须由用户决定的商业条件三栏表。合同期限、试用期、岗位、地点、工资数额与构成、奖金承诺、特殊工时、竞业与服务期、知识产权安排、签署主体和生效日均不得自行补齐。

法律上的后备规则或上限不是商业条件默认值。期限、岗位、地点、报酬或工时任一核心条件未决定时，只能形成条件确认表和受限骨架；但有权单位已经决定、内容完整合法且无冲突的条件可以写入供劳动者签署接受的完整版本，不因劳动者尚未签字而停止。

试用期把商业选择和强制规则分开：是否设置及具体期间由单位拟议并供签署；期限上限、同一劳动者一次、包含在合同期内、工资底线和解除条件／说明理由分别核验。社会保险法定义务可依法成条，动态申报参数未核数不当然阻断整份合同。

### 3. 强制规则与特殊人员

按 `用工地 × 人员类型 × 工时制度 × 行业或岗位危害` 建立规则矩阵，逐项核验最低工资、工资支付、工时休假、加班、试用期、社会保险、劳动保护和特殊保护。

外国人、未成年工、非全日制、派遣、达到法定退休年龄或处于弹性延迟退休等状态必须先分流。按影响选择 `停止整个可签状态`、`停止生效／到岗` 或 `仅停止专项条款`，不得一律降为普通字段缺口。

外国人只有旅游签证时，明确其不是工作授权，许可和工作类居留完成前不得实际到岗。先核验人员例外、单位、岗位、地点、期限、许可申请是否需要预签文本及现行司法控制，再给两条受限路径：许可齐备后签署并到岗；或专项官方规则允许且申请许可确需合同时，预签明确的附许可条件文本，但不得在准入完成前实际工作。不得笼统宣称所有合同都不能先签。

用户仅错误要求“按普通员工直接起草”、要求保证效力，或尚未核实许可状态，并不自动等于其坚持伪造身份、隐匿许可或安排提前工作。此类请求先纠正错误目标，保持正触发，输出完整受限文件包和上述两条路径；只有用户在获知边界后仍明确要求伪造身份／许可、隐瞒旅游签证、虚构已获批或在许可前实际用工，才按欺骗性要求整体停止。

### 4. 文件一致性与附件接口

按字段核对 offer、单位审批、集体合同、规章制度、岗位说明、劳动合同和附件。每一冲突记录来源、文字、时间、适用范围、受影响字段和有权确认人；不得静默选择成本最低、对单位最有利或时间最新但未经核验的版本。

两份或多份冲突材料即使当前不可完整读取，也分别登记，不得汇总成一个来源编号。已读取且完成来源审查的按适当 `D#/L#/P#` 登记；只知道用户描述的，至少分列 `S1`、`S2`，把各自机关、层级、日期、版本、对象和适用范围标为已知值或 `未提供`，并在冲突表中逐栏给出关闭缺口。

附件分为 `合同组成文件`、`仅确认签收／知悉的制度文件`、`内部工作底稿`。只有合同组成文件进入 `V#` 附件索引；写明名称、版本、日期、适用人员、是否共同签署和冲突处理。保密、职务成果、专项培训服务期、竞业限制等事实不足时，主合同只保留中性接口和未决项，不代做独立专项方案。需要独立发展的相似 Skill 不构成本 Skill 的固定依赖。

### 5. 版本、签署、交付和归档

草案形成不等于已经签署、生效、交付、备案或实际履行。定稿时建立唯一 `V#`，记录正文哈希、每个合同附件哈希、附件索引和签署页映射；不得与来源 `D#` 共用编号。

每个 `E#` 至少记录动作类型、操作者、权限来源、真实时间、对应 `V#` 和哈希、证据对象、渠道、签收或审计日志、验证结果。纸质路径核对同版签署、双方各执完整文本和签收；电子路径分别核对身份、意愿、可靠签名、可信时间、防篡改、完整文本取得、交付和日志导出。测试夹具必须标明为 fixture，不得冒充现实动作，也不得实际调用平台。

补签必须区分真实签署日和既往实际用工期间。不得倒签、复用跨版本签署页、让劳动者签空白页或虚构已经协商一致。用户接受如实路径后，可在无既发争议时恢复起草，但不得写此前已经签署、全部条款当时已合意、既往无争议、责任豁免或权利放弃；明确本次补签不自动消除既往法律后果，本 Skill 不判断二倍工资、和解或责任结论。

## 停止与安全

- `整体停止`：基础主体或法域无法建立；用户坚持以虚假事实为前提；要求伪造、倒签、虚构协商、隐藏实际用工、虚假拆分工资或规避强制标准。
- `字段停止`：核心商业条件未决；文件冲突未闭合；地方参数、特殊身份、许可、批复、规则或签署能力未核验。
- `机关决定边界`：许可、审批、登记、材料真伪或争议结论须由有权机构决定时，不冒充机构作出结论。

首次收到欺骗性要求时立即拒绝并停止合同正文，只提示保留真实资料、如实记载，并邀请用户明确同意改为基于真实事实起草。用户明确同意后，从真实事实重新建立起草坐标；用户坚持时整体停止，不提供规避措辞、替代交易结构、关系识别技巧或相邻任务成果。

“欺骗性要求”在本节特指以虚假业务事实、虚假身份／许可、虚假双方合意或虚假签署实施动作作为合同正文或现实执行前提。用户要求把自制文件、普通附件或口头声明错误升级为 `L#／P#／已核验` 时，必须拒绝来源升格和可签终稿，但这只是来源字段及可签状态停止：将材料按 `S#/D#` 如实登记，并继续输出 1—13 节完整受限文件包。只有用户进一步要求伪造宿主签名、调用日志、底层法源、哈希或其他证据，或者坚持以该虚假来源实施现实签署，才按安全整体停止。

## 交付与质量检查

严格按 [输出合同](references/output-contract.md) 交付，提交前确认：

- 任务确属单位侧新劳动合同起草，未代做招聘、审查、制度、专项协议或争议成果；
- 主体、人员、法域、核心条件、规则和文件冲突均有来源编号与状态；
- 来源登记表能把每个核心命题回到唯一记录；`S/D/A/R/L/P/I/G/V/E` 不串类；
- 未把单位拟议、材料表面内容或法定后备规则写成双方合意；单位拟议完整时可形成供签署版本；
- 条件未决或来源未核验时，只形成受限草案并明确停止字段；
- 正触发且用户要求起草时，即使成果受限，也已输出完整受限文件包，而非只有来源表、短骨架或恢复条件；
- 合同正文达到 [输出合同](references/output-contract.md) 的最低可签结构；合同附件、内部底稿、商业条件表、规则表、冲突表和实施清单彼此一致且不混类；
- 未声称尚未发生的签署、生效、交付、审批、备案或履行已经完成；
- 未保证条款必然有效、没有争议或必然胜诉；
- 正触发的成果完成状态逐字使用 `已形成`、`部分形成并明确受限字段`、`因停止条件未形成` 之一；负触发不填写成果完成状态。

相邻任务只按本次目标路由，见 [边界与路由](references/routing.md)。
