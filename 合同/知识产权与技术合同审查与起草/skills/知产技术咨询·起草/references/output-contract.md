# 输出合同

正触发固定十节，除安全整体停止外不得省略。负触发只写触发判定、路由和最小交接，不填十节实体结论。

判断只用 `现有依据支持`、`现有依据不支持`、`依据不足，无法形成结论`。正触发成果状态只用 `已形成`、`部分形成并明确受限字段`、`因停止条件未形成`。

禁止：只打红黄绿不给修改句；保证有效、对方接受或必然可执行；编造未给出的报酬、费用、工期；把已失效《合同法》《技术合同法》及其实施条例写入结论；保证研发成功、立项获批或固定降本；把第 881 条第 3 款写成无条件免责；把费用写成依法由委托人预付；把开发、商务咨询或委托货架文本当成已完成的本类型审查。

## 1. 触发、单方立场与成果状态

立场、授权、签署状态、主要目标。负触发写路由，不启动实体审查。写明中文成果名称是「审查技术咨询合同（技术类合同）」。

## 2. 来源登记与 MCP 调用表

`S/D/A/C/L/I/G`。MCP 未调用也留一行状态：`not-registered` / `permission-denied` / `error` / `no-result` / `partial` / `conflict` / `verified-result`。`search_law` 返回已失效《合同法》及其解释、已失效《技术合同法》或其实施条例时，记噪声，不得写入 `L#`。

## 3. 类型与加载路径

父级 `技术类合同`，子级 `技术咨询合同`。定性理由、易混切开结果（开发 / 商务咨询 / 委托侧 / 技术服务 / 出图）。加载路径必须写成：`references/基本面.md` 与 `references/框架.md`。写明只读这一对、未通读其他类型。知识库与硬闸冲突时，以 method 硬闸为准。

## 4. 主体、专家与文本版本

主体表：签约名、履行名、付款名、发票名、授权签字人。专家表：岗位或名单是否锁定、与评价对象有无利益关联。版本表：正文、技术任务大纲、数据清单、聊天确认；冲突并列。

## 5. 给付闭环：意见标的、881、费用、归属与验收

是否特定技术项目；交付是否仅为可行性或技术方案意见；是否出现研发成功/保过/固定降本保证；881 自负是否写明“报告符合约定要求”；886 费用由谁负担；报告使用权与 885 新成果是否分项；报酬与节点；验收是否绑投产或盈利。缺口标 `G#`。不输出开发风险分担或委托任意解除口径。

## 6. 格式条款与强制规范

是否构成格式条款；提示说明痕迹。无条件决策赔偿、排除故意或重大过失的免责必须改。强制规范只按第 153 条区分，不用失效口诀。技术进出口或国家秘密未批准：履行字段停止。无 `search_law` 引文则本节点法律结论字段停止，事实摘录和修改句草稿继续。

## 7. 风险表（必须回链文本位置）

固定列：`编号｜文本位置｜原文摘录｜问题｜判断｜级别｜修改句或红线｜来源｜最强反方`。

级别只用 `红线`、`必须改`、`可接受可优化`。每一行必须有修改句或明确停笔/转出口径。

## 8. 修改句

按已加载 `框架.md` 的六步组织：首部、交易条款、配套、尾部、语言、常见问题。每条含：定位、原句、建议句、理由、可退让点。未给出的商业数字用 `【待填】`。不得把“咨询报告著作权无约定归某一方”写成法定默认。

## 9. 谈判与签署提醒

谈判顺序：先红线（不是可行性/技术方案意见、研发成功/保过/固定降本保证、881 无条件赔偿、虚假可行性、未批进出口），再必须改（任务大纲要点、资料协作、886 费用、885 分项、验收不绑投产），最后可优化。签署提醒：授权、用印、日期、任务大纲与数据清单、专家名单附件。不指导倒签或保过。

## 10. 缺口、停止项与提示

`G#`、字段停止、整体停止、转介。审查模式成果不是整份起草终稿；起草模式见文末。不是履约交底、争议文书或效力保证，也不是技术开发、商务咨询或委托事务安排。
