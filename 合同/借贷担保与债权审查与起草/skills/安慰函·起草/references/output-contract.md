# 输出合同

正触发固定十节，除安全整体停止外不得省略。负触发只写触发判定、路由和最小交接，不填十节实体结论。

判断只用 `现有依据支持`、`现有依据不支持`、`依据不足，无法形成结论`。正触发成果状态只用 `已形成`、`部分形成并明确受限字段`、`因停止条件未形成`。

禁止：只打红黄绿不给修改句；保证有效、对方接受或必然可执行；编造未给出的金额、期限；把已失效《合同法》《担保法》及其解释写入结论；把解释第八条写成担保意思条文；把本函改成保证或见索即付后按本类型放行；输出起诉策略；写未登记则函件未生效。

## 1. 触发、单方立场与成果状态

立场、授权、签署状态、主要目标。负触发写路由，不启动实体审查。写明中文成果名称是「审查安慰函（保证合同）」。

## 2. 来源登记与 MCP 调用表

`S/D/A/C/L/I/G`。MCP 未调用也留一行状态：`not-registered` / `permission-denied` / `error` / `no-result` / `partial` / `conflict` / `verified-result`。`search_law` 返回已失效《合同法》及其解释、已失效《担保法》及其解释、法发〔1994〕8 号，或把解释第八条写成担保意思、把框架做硬写成已核验规则时，记噪声，不得写入 `L#`。

## 3. 类型与加载路径

父级 `保证合同`，子级 `安慰函`。定性理由、保证意思分层结果（道义／有担保意思／债务加入／难分按保证认定／依据不足）、易混切开结果（一般保证／连带保证／最高额／独立保函／增信主文件／保证借款）。加载路径必须写成：`references/基本面.md` 与 `references/框架.md`。写明只读这一对、未通读其他类型。知识库与硬闸冲突时，以 method 硬闸为准。

## 4. 主体、决议与文本版本

主体表：债权人、债务人、出具人、签约名、授权签字人、决议机构。禁入与决议闸：机关／公益主体、是否可能被定性为担保或债务加入、章程限额、股东或实控人担保回避、上市公司披露。版本表：函件正文、主债权或授信协议、决议、授权委托、债权人回函或签收稿、聊天确认；冲突并列。

## 5. 保证意思、支持方式与接收

硬词／软词原句及分层判断；支持方式（流动性／持股／净资产／不抵押承诺）是否仍停留在函内姿态；债权人是否接收或拟回函；685 第二款是否被错误套用到软函。缺口标 `G#`。不输出“一定是保证”或“一定只是道义”的终局结论，也不输出唯一应付金额。

## 6. 强制规范与禁止做硬

机关／公益禁入；公司决议或越权；上市披露；独立性／见索即付夹带句。无 `search_law` 引文则本节点法律结论字段停止，事实摘录和删除句草稿继续。不得把“改成代为清偿／见索即付／本文件构成保证担保”写成建议句。

## 7. 风险表（必须回链文本位置）

固定列：`编号｜文本位置｜原文摘录｜问题｜判断｜级别｜修改句或红线｜来源｜最强反方`。

级别只用 `红线`、`必须改`、`可接受可优化`。每一行必须有修改句或明确停笔／转出口径。

## 8. 修改句

按已加载 `框架.md` 的六步组织：首部、交易条款、配套、尾部、语言、常见问题。每条含：定位、原句、建议句、理由、可退让点。未给出的商业数字用 `【待填】`。必须至少有：一条保证意思分层句；一条与独立保函或增信主文件切开或排除见索即付／差额补足主路径的句子。框架里的做硬句不得直接当作建议句。

## 9. 谈判与签署提醒

谈判顺序：先红线（机关／公益硬函、做硬改保证或见索即付、无文本仍要放行、倒签、假决议），再必须改（硬软词冲突、标题名实不符、债权人未签收、可能构成担保却无决议／披露、追偿空白），最后可优化。签署提醒：出具人签字或盖章；若可能构成担保或加入则决议／披露作为附件；债权人侧回函确认收到但不把回函写成已经接受保证（除非用户已转保证原子）；出具人侧在显著位置保留“不构成保证或法律担保义务”的反说。不指导倒签、补假决议或起诉策略。

## 10. 缺口、停止项与提示

`G#`、字段停止、整体停止、转介。本任务交付可编辑草稿、未决项、自审风险表与自审后修改句。草稿必须覆盖本类型起草必写、附件必附与禁止出现。有完整待签文本要评改时转配对审查原子。不是履约交底、争议文书、保证责任评估或效力保证。
